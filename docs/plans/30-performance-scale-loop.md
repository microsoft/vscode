# Plan 30 - Performance and scale (surviving the first real folder)

> **For agentic workers:** implement with `superpowers:subagent-driven-development`.
> Small, live-verified, stacked PRs off `main`.
> Context of record: [11-product-review-2026-07.md](../11-product-review-2026-07.md) findings P2-1 and P2-3; the risk register called these out from the start ([04-risks-and-predictions.md](../04-risks-and-predictions.md) "Scaling / performance predictions").

**Goal:** A 50-document folder with a dozen sources behaves: refresh derives only what changed, network and model calls run concurrently with limits, the fan-out respects the model's context window with an explicit (never silent) inclusion policy, and a scale fixture + measurement harness make regressions visible.

**Architecture:** All changes inside `contrib/livingDocs/`.
Four independent tracks: (1) incremental, source-scoped derivation replacing the all-docs sweep; (2) a small concurrency-limited scheduler for network/model calls; (3) context budgeting for the plan-18 single-call fan-out (decision 62) with a chunked fallback; (4) a generated scale fixture + timing harness in the test suite so numbers are tracked, not guessed.

**Tech stack:** existing contrib; `vs/base/common/async` primitives (`Limiter`/`Throttler` - use them, do not hand-roll); the existing `IClock` seam (`browser/clock.ts`) for deterministic tests.

## Global constraints

- Behaviour-preserving at small scale: the sample-folder demos must produce identical results (same proposals, same audit entries) before/after each iteration.
- **No silent truncation** (the plan-23 honesty rule): whenever budgeting drops or defers a document, the UI says so.
- Rate-limit awareness: unauthenticated GitHub is 60 req/h/IP ([04](../04-risks-and-predictions.md)); per-source cooldowns are part of correctness, not polish.
- Tabs; nls strings; disposables (schedulers are disposables); Australian English; no em dashes.
- `typecheck-client` + `valid-layers-check` clean per PR; timings recorded in `docs/plans/30-verify/notes.md`.

## Current state (exact anchors)

- `refreshFromSources` (`common/livingDocs.ts:245`, impl in `livingDocsService.ts`): iterates every discovered doc serially; each api block fetches, each narrative block may call the model.
- Orchestrator: `runDueAgents` (`browser/agentOrchestrator.ts:180`) awaits agents strictly in sequence; the dirty queue (`:259`) exists and is drained by the heartbeat - the *scoping* mechanism is already there, the refresh path just does not use it for manual refreshes.
- Fan-out: one model call carries every working-set doc body (decision 62); `parseMultiChatResponse` (`common/livingDocMarkdown.ts:412`) parses the keyed reply; `MODEL_MAX_TOKENS = 1024` output cap in the proxy.
- Webview: mount-once-then-message (decision 50) already avoids re-inlining the 496 KB PM bundle; whole-screen HTML re-render remains for screen surfaces (acceptable; screens are small).
- Discovery: a directory scan of the loaded docs' folders; no index.

## Decisions to settle in iteration 1

- **D30-A - concurrency limits.** Recommendation: 4 concurrent source fetches, 2 concurrent model calls, per-source-host cooldown of 30 s between identical fetches (cache the response body + hash within a refresh pass so N docs bound to one CSV/API read it once).
- **D30-B - fan-out budgeting policy.** Recommendation: estimate tokens (`chars/4` is adequate); pack docs into the single call up to a budget (model context minus prompt minus safety margin, configurable `livingDocs.fanoutContextBudget`, default 24k tokens); overflow docs run in additional batched calls (same instruction, next N docs) rather than being dropped; the run screen shows `batch 2 of 3` in the command strip.

## Iteration plan

### Iteration 1 - Measure first (the harness and the fixture)

- Add a fixture generator under `test/browser/` (pure function, also usable as a script): `makeScaleFixture(docs: number, bindsPerDoc: number)` producing in-memory doc+lock pairs bound to a handful of shared sources.
- Timing harness: a unit-style test (marked slow, skipped in CI by default via suite filter) that loads 50 generated docs through the service against a mocked file service + stubbed fetch/model, and records: full refresh wall-time, count of source reads, count of model calls.
  Assert on the *counts* (deterministic), record the times to console.
- Also create an on-disk sample: `living-docs-scale-sample/` generated by a small script in `scripts/` (50 docs, 3 CSVs, 1 api source) - gitignored except the generator.
- Gate: baseline numbers captured in `30-verify/notes.md` (e.g. "50 docs: 150 source reads, 50 model calls, serial").
  These are the before-numbers every later iteration beats.

### Iteration 2 - Incremental derivation + shared-source caching

- Refresh takes a scope: `refreshFromSources(resource?)` gains an internal plan step that computes affected docs from the changed sources via the orchestrator's reverse edges (the dirty-queue data, `agentOrchestrator.ts:259`) instead of sweeping all docs; the manual toolbar Refresh on a doc scopes to that doc; the project-level refresh scopes to docs whose sources' hashes actually changed (hash check first, cheap, already implemented in `_recomputeFreshness`).
- Within one refresh pass, cache each source read (`Map<sourceId, { body, hash }>`), so a CSV bound by 20 docs is read once.
- Tests: with the 50-doc fixture and one changed CSV, only that CSV's dependents re-derive; source read count == changed sources, not docs x blocks.
- Gate: harness counts drop to the asserted values; sample-folder behaviour unchanged (same proposals for the standard week-24 change).

### Iteration 3 - Bounded concurrency

- Introduce a scheduler in the service using `Limiter` from `vs/base/common/async` per D30-A: source fetches (limit 4) and model calls (limit 2) run concurrently within a refresh/agent run; per-host cooldown map for repeat fetches.
- `runDueAgents` may keep agents sequential (agents are few); the *inside* of a run parallelises per-doc derivation with the same limiters.
- Cancellation: thread the plan-27 `CancellationToken` through the scheduler so Stop-run drains cleanly (if plan 27 has not landed, take the token parameter now and wire the UI later - state the dependency in the PR).
- Tests: with a fake clock + deferred promises, assert at most 4 fetches in flight; a rejecting fetch fails only its doc (others complete); cooldown suppresses an identical fetch within 30 s.
- Gate: harness wall-time drops correspondingly (record); no interleaving corruption (proposals still keyed to the right docs - assert via the existing service tests re-run against the concurrent path).

### Iteration 4 - Fan-out context budgeting

- Implement D30-B in the fan-out path (`sendChatMessage` working-set branch / the project-run composer in `livingDocsService.ts`): token-estimate each doc body, pack to budget, emit batches; merge the per-batch keyed edits before queueing proposals (`parseMultiChatResponse` output concatenation - watch for duplicate doc keys across batches; last batch wins is wrong, assert uniqueness by construction since each doc is in exactly one batch).
- Run screen: command strip shows `batch K of M`; per-doc tiles set "queued" state until their batch starts (truthful states, plan-23 rule).
- A doc larger than the whole budget is not sent: its tile reads "too large for this run" (amber) with a doc-level hint - never a silent drop.
- Tests: packing (respects budget, preserves order, singleton oversize flagged); merge (edits from 2 batches queue for the right docs).
- Gate: a 50-doc live run on the scale sample completes in batches with truthful strip/tiles; the oversize case renders its amber state.

### Iteration 5 - Webview-layer test seams (the P2-3 debt)

- Extract the pure message-protocol logic out of `livingDocEditor.ts` and `screenEditor.ts` into `common/` reducer-style functions (`applyEditorMessage(state, msg) → { state, effects }`) - the pattern the existing tests already use for `screenRender`.
  No behaviour change; the webview classes become thin shells.
- Add unit tests for the extracted reducers covering the mount-once lifecycle: pmReset ordering, pending-update-while-hidden, focus-after-navigate (the plan-19 rail-to-editor bridge).
- Gate: ~20 new tests; `livingDocEditor.ts` and `screenEditor.ts` shrink measurably; live smoke of open/edit/approve/navigate unaffected.
