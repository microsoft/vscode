Proposal, feasibility, and architecture

Feasible incrementally, not fully available out of the box. Workspace-less means no folder is required to begin. It does not mean code runs without a filesystem, permissions, or a provider. This file is a visual proposal, not an integration or proof of backend availability.

Reuse today

  • Workspace-less quick chats on capable providers.
  • Sessions, nested chats, custom groups, pins, archive, and filters.
  • Provider-mediated repository selection and Git cloning where supported.
  • Local and remote Agent Host sessions; experimental cloud-sandbox provisioning.
  • Image attachments and provider-reported artifacts and references.

New product work

  • This dashboard and intent-to-context recommendation flow.
  • Explicit confirmation of repository, environment, and permissions.
  • Linked handoff from quick chat to an execution session, without rewriting its identity.
  • Provider-neutral preparation progress and durable recovery.
  • Named execution presets (“recipes”), validated by their owning provider.

Do not promise

  • Arbitrary cloud machines, sizing, pricing, or universal recipe execution.
  • Reliable repository inference without evidence or user clarification.
  • A stock model understanding uploaded video or a universal recorder.
  • Cross-provider chat migration, automatic permission bypass, or guaranteed background execution.
  • Archiving a task shutting down billable compute.

Organization: one intent, not one chat per tool call

“Task” is a user-facing label for a session in this first iteration, not another backend task store. Keep one primary chat; additional verification or investigation chats stay inside that session when supported. Tool calls remain in the transcript. Pin important sessions, move them into optional groups, search, and archive finished work. Do not automatically regroup work after a user organizes it.

A quick chat that needs a different repository or compute provider creates a separate execution session through existing management operations. A proposed handoff records a visible source link and carries only approved context; it does not pretend that chats can move between providers. Existing custom groups can collect these related sessions. Their memberships remain local presentation state, not an execution boundary.

Architecture fit

  • Add a Sessions-owned AbstractCustomView dashboard through ICustomViewService. Opening a session dismisses the dashboard and returns to the existing chat/detail layout. No new workbench part or embedded production HTML app.
  • ISessionsManagementService owns orchestration and provider routing; ISessionsService owns active/visible sessions. Cards derive from their observables, not a second session store.
  • Use ISessionGroupsService and ISessionsListModelService for organization. Preserve archived > pinned > custom group > quick chat > workspace/date placement.
  • Keep provider implementations isolated. New provisioning/preset contracts belong in shared interfaces; only providers call backend APIs. vs/workbench must never import vs/sessions.
  • “Preparing”, “cloning”, and “testing” are proposed progress details, not new values invented in SessionStatus. Report only observed events. Disconnected is connection state, not proof that the agent stopped.
  • Respect AI-disabled UI gating, model and provider capabilities, authentication, workspace trust, and runtime-managed permissions. Confirmation in this UI never replaces runtime enforcement.
  • Production uses existing widgets, theme tokens, localized labels, scoped menus, disposal, accessibility help, an accessible view, and a verbosity setting.

Phased delivery and exit criteria

  1. Dashboard first: project existing sessions into a custom view; reuse organization and open actions. Verify keyboard navigation, themes, filtering, pin/archive precedence, and no duplicate session identities.
  2. Intent intake: reuse quick chat and attachments; ask for missing context and present editable recommendations with reasons. Verify ambiguous requests, unsupported providers, AI-disabled mode, and consented handoff.
  3. Prepare execution: reuse clone/worktree and available host paths; introduce provider-neutral preparation progress and recovery. Test cancellations, failed clones, expired authentication, duplicate sends, reconnects, and persisted operation identity before adding retry.
  4. Evidence and presets: surface provider artifacts; add capture only for runners that support it. Treat videos as files/links unless the selected model explicitly accepts them. Gate recipe support on real backend contracts for validation, lifecycle, cancellation, cost visibility, and cleanup.
