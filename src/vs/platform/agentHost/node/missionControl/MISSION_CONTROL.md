# Mission Control environments

Mission Control exposes VS Code's existing native Agent Host utility process as a user-local environment over Azure Web PubSub. Local sessions continue using local IPC; remote clients use the same authoritative session state and protocol handler, not a separate daemon.

```text
Local VS Code ------ local IPC ------+
                                    +--- one native Agent Host and session state
Other clients ----- MC / WPS --------+
```

Registration is opt-in and default-off. The activation path is available to built desktop products as well as source builds; unsupported host variants do not acquire it merely because an AHP client requests a connection. The feature remains tagged experimental. [Readiness and remaining validation](./MISSION_CONTROL_PRODUCTION_GAPS.md) must not be confused with a guarantee about every release artifact or deployed client.

## Enable the real service

1. Sign in to GitHub in the owning VS Code window.
2. Set `chat.agentHost.remoteConnections` to `githubEnvironment` (the default is `devTunnel`).
3. Enable **Allow Remote Connections** in the Agents Window title bar or the local Agent Host chat toolbar. Selecting GitHub environment in settings does not register the environment.
4. Wait for `Mission Control ready; environmentId=...` in the Agent Host log.
5. Create/use native sessions normally. From another compatible MC client, discover the environment, connect, authenticate with a sealed credential, and use standard AHP session operations.

Registration uses `https://api.github.com`. Desktop sharing grants `/` on macOS/Linux and available local drive-letter roots on Windows, plus home and local project folders. The advertised starting directory is home, including in an empty window. Authenticated owner clients can read and modify accessible files, including sensitive files; operating-system permissions still apply. The recent-folder project catalogue is separate from filesystem access. Clients use standard AHP `defaultDirectory` and resource commands to browse; users can enter an absolute path to another location or drive. Network-backed Windows drives and unmapped network shares are not included in local drive enumeration. Disable **Allow Remote Connections** to withdraw remote access. The sharing choice is remembered locally across restarts, not synchronized to other machines. Changing the backend turns sharing off until explicitly enabled again. Withdrawal disconnects relay ingress immediately; it does not delete native sessions, conversations or checkouts.

Registration and heartbeat `capabilities.current_sessions` count durable session-registry identities, independently of sidebar filters and provider availability. Counting does not load provider metadata or session transcripts. Metadata reads have a 60-second budget; a failed or timed-out device remote-control policy read prevents registration unless the explicit local policy override below is enabled.

### Local integration testing

Backend tests supply `IMissionControlOptions` directly to `MissionControlEnvironment.configure`, with a loopback HTTP `baseUrl` and `live` omitted or false. Test credentials and injected HTTP/relay implementations keep registration and authentication tests independent of the real service.

The backend setting's experimental feature tag does not restrict availability to development builds.

## Environment identity, name and ownership

The registered name is `VS Code`, `VS Code Insiders`, or `VS Code OSS`; other product variants use their product short name. The same host-owned name is sent on registration and every heartbeat. This display label is not identity.

A random stable compute UUID is persisted in `agent-host-mission-control-id` under the user-data directory. It is not derived from hardware. The versioned record retains its canonical directory only locally, so a migrated profile copied to another directory receives a different identity without changing the original. Legacy plain UUIDs migrate in place; copies made before migration remain an explicit edge case. Restarting the same profile reuses its identity. Separate user-data directories intentionally represent separate hosts and may have identical display names.

The first accepted account owns the shared utility process until restart. Same-owner windows may refresh the credential and contribute canonical workspace roots, without rebinding the active registration's default directory. Foreign-account configuration/withdrawal is refused. Genuine withdrawal clears the active grants/default; a later same-owner registration establishes new ones. Identity-authority changes withdraw access rather than silently rebinding the host.

## Discover and connect

Enable `chat.remoteAgentHostsEnabled` and invoke **Connect to Mission Control Environment...** from the Command Palette or Agents Window workspace-management menu. The picker lists your account's existing user-local environments, shows cached results immediately, and refreshes in the background without clearing the search. It excludes the native host's own environment so the owning window stays on local IPC.

Selection revalidates availability. An offline user-local host is not woken or replaced; start its owning application before connecting. Discovery itself does not provision compute or create sessions. Connected user-local hosts use the generic native Sessions provider, not the managed-sandbox task/history/checkout adapter. The fuller retained-host/management UX is a separate increment.

New native allocations negotiate standard `ahp-session` resources with a separate provider. Existing legacy and standard session/chat resources, SDK backings, and storage remain immutable. The client consumes exact advertised resources; MC does not impose a global Copilot alias. See the [identity contract](../../../../sessions/contrib/providers/agentHost/AGENT_HOST_SESSIONS_PROVIDER.md#identity).

Mission Control excludes external sessions from `listSessions` responses and session catalogue additions and updates, independently of `chat.agentSessions.showExternal`. Its `listSessions` response includes all remaining visible non-archived sessions and at most 100 archived sessions, selected by most recent modification time after visibility and workspace-grant checks. `MissionControlHost` supplies these filters through the listener's optional session-summary filter and session-list adapter; local, SSH, and tunnel listings are unchanged. The cap does not delete archived sessions or prevent subscribing to older sessions by their advertised resources.

Before relay identity authentication, clients may call `authenticate`, `listSessions`, `resolveSessionConfig`, `sessionConfigCompletions`, `extensions/listProjects`, `subscribe` to the root channel, and `unsubscribe` from their own subscriptions. Connection lifecycle requests (`initialize`, `reconnect`, and `ping`) also remain available. Reconnect restores only root discovery before authentication; requested session channels are withheld until the client authenticates and subscribes again. Claimed active-client participation is retained while awaiting authentication, without streaming session content.

Unauthenticated listings and basic catalogue notifications omit `_meta`, `chats`, and `defaultChat`, which can expose session content, but retain discovery fields such as titles, status, and working directories. Detail-only summary changes are not sent. Root discovery includes the full host configuration and project catalogue before AHP authentication, including live updates and reconnect replay, but omits terminals and agent customizations. These projections run when responses or notifications are sent, so an expired identity receives the same discovery data. Session content, non-root subscriptions, and mutations still require the authenticated owner identity; unknown methods are not exempt. Local IPC, SSH, and tunnel listings do not require a Copilot credential and retain their full summaries.

### Web PubSub receive capabilities

VS Code clients publish the transport control `{"kind":"capabilities","accepts":["batch"]}` to the configured `to_host` group after joining their receive groups, and wait for its relay acknowledgement before initializing AHP. The socket/group-join timeout ends when the joins complete; capability publication then has its own 30-second acknowledgement deadline. They re-advertise after each successful AHP initialization or reconnect response, before delivering that response to the protocol client, so a replacement host lane can establish receive support. Rejected, timed-out, or unwritable capability publications fail the connection through normal relay error handling.

The declaration permits a supporting peer to send bounded, ordered transport batches toward VS Code; it does not enable client outbound batching or prove that the peer has processed the declaration. Individual messages and chunks remain supported. These controls are not AHP messages or JSON-RPC batches and are not emitted on direct WebSocket or local IPC connections.

### Model advertisements

Mission Control connections intentionally advertise model lists only for the native Copilot agent (`copilotcli`). Other agents remain advertised with their identities, capabilities and protected resources, but with empty model lists. This is the client interoperability scope for mobile clients that combine every agent's models into the picker for an existing Copilot session without switching that session's agent. Initial and subscribed root snapshots, reconnect snapshots/replay and live agent updates use the same projection; the host's authoritative catalog and local, SSH and tunnel connections remain unchanged.

Existing sessions for other agents remain visible and retain their model selection. Model filtering alone is not an execution authorization boundary and does not correct a credential-specific empty Copilot catalog. Mission Control protected execution separately requires the provider to declare `supportsScopedCredentials: true` and obtain the required credentials from the supplied host-owned source. The native Copilot provider is the supported implementation of that capability; other providers fail closed for scoped protected execution rather than falling back to desktop credentials. This Copilot-only execution scope does not remove other providers from observation or claim all-provider sponsorship.

## Security and data handling

The [security requirements matrix](./MISSION_CONTROL_SECURITY_REQUIREMENTS.md) links each requirement to implementation and tests. The supported boundary includes canonical-owner sealed authentication, signed control requests, lane/client-ID binding, passive mutation refusal, locally known workspace/resource grants, and restricted pre-authentication session discovery. Relay transport admission permits reading the full host configuration, including values that may contain credentials, without a separate AHP identity credential. Editing Host Settings requires an authenticated active owner client. Passive clients remain read-only. Remote windows do not automatically synchronize their local settings or managed permissions into the owning machine.

Rejected mutations on passive connections return a user-facing read-only connection message, including session-creation RPC errors and message-dispatch rejection reasons. The host does not attribute passivity to enterprise policy or SSO because the signed spawn request carries no reason for the restriction.

Live relay identity expires at the deadline returned by GitHub in `GitHub-Authentication-Token-Expiration`, not a client-supplied timeout. Supported deadlines are calendar-valid UTC timestamps in GitHub's `YYYY-MM-DD HH:MM:SS UTC` format or ISO `YYYY-MM-DDTHH:MM:SS[.sss]Z` format with up to three fractional digits. Invalid or elapsed deadlines fail authentication; an absent header does not create a deadline. Expiry stops session-content observation and new protected work, removes non-root subscriptions, releases active-client/tool ownership not retained by another live connection's subscriptions, and sends one lane-targeted `auth/required` notification with `reason: expired`. Root discovery remains available. The client must renew its credential and subscribe again to session content. Awaited requests cannot return protected results under an expired or replaced credential. Work already admitted to a provider is not rolled back; its captured-credential lifetime is separate from lane authorization.

Remote owner access includes native sessions, tools, and granted workspace resources. Credentials are sealed before WPS publication using either NaCl sealed boxes or HPKE (X25519 / HKDF-SHA256 / AES-256-GCM). The host advertises independent keys for each algorithm and for each of the `auth-token` and `mcp-auth-token` purposes, allowing clients such as iOS to use HPKE while sealed-box clients remain compatible. Recipient keys come from authenticated MC HTTPS rather than being trusted solely because they appeared in the relay. Private sealing keys stay host-local. Sealing alone does not establish per-client/session credential sponsorship, OS confinement, or conversation end-to-end encryption.

Clients must authenticate the relay identity after each handshake before requesting session content or mutations, independently of agent-provider authentication. Unauthenticated protected requests return `AuthRequired` with standard `data.resources` identifying the configured GitHub identity authority, including hosts without a Copilot provider. Owner-validated identity authentication can establish lane identity even without provider acceptance. Scoped protected execution additionally requires a credential-capable provider and its required resource credentials; provider/MCP resource authentication is not implied by owner identity.

Same-owner credential renewal before the current GitHub-reported deadline preserves in-flight requests and subscriptions. Expiry or a new handshake invalidates previously admitted work, even after successful reauthentication. Renewal checks the previous deadline before replacing it, so delayed expiry timers cannot hide a lapse.

### Native GitHub credential lifetimes

Scoped connection authentication holds one current credential per protected resource. A newly authenticated grant replaces that resource's previous grant, including when the new scopes are narrower; new work cannot recover an older, broader scope grant from a pool. Already admitted work retains its independently captured grant until that grant expires or is revoked. Replacing the connection's current credential neither upgrades an existing snapshot nor creates additional current scope slots.

Native changeset operations capture requester credentials at admission, before waiting for another operation or repository work. PR, commit, merge and sync refresh callbacks carry that snapshot into their Git-state derivatives. GitHub clients, project clones and pull-request worktree provisioning use captured resource grants rather than rereading a connection's newer token. Snapshots retain their original expiration and observed revocation checks; expired or observed-revoked grants fail through the existing authentication errors and logs, without selecting a global credential. A closed connection source cannot admit a new capture. Source-supplied project clones additionally isolate their Git configuration and environment to exclude ambient authentication. This does not replace authentication for other Git subprocesses or add an OS-level confinement boundary.

Changeset-operation retries deduplicate only within the same source and captured grant generation. Capture and validation happen before looking up an in-flight result, so credential rotation or connection disposal cannot reuse an older operation's success. Deduplication keys contain resource metadata and host-local weak grant identities, never token values; mutation lanes still serialize operations across generations.

Session-only pull-request status watchers and lifecycle checks are host-derived work: they capture the session's sponsor when scheduled and never choose an arbitrary peer chat. One background sync retains that snapshot across awaited folder lookups and coalesced retries; an installed watch retains its original client until it is stopped or replaced. A later, separate watch or reconciliation may capture a newly supplied sponsor. Automatic association captures the session source at scheduling unless an initiating chat or operation supplies an explicit source; recorded-artifact reconciliation captures each recorded chat's source independently. Agent Merge uses an explicit operation binding when present, otherwise follows its configured chat's execution sponsor, and captures the repository and optional Copilot API grants before evaluation. Repair turns carry that runtime snapshot without replacing the chat's execution binding. Creating a session with Agent Merge enabled, explicitly enabling or changing monitoring, or creating a pull request with Agent Merge captures the initiating sponsor independently. Removing an explicit binding returns monitoring to the execution-sponsor default; a failed configuration change restores only the previous explicit binding. Sessions marked isolated but lacking a usable sponsor cannot fall back to legacy authentication. Sessions with no isolated principal retain the legacy credential path.

Background Git-state refreshes continue updating local branch and dirty state when a restored or disconnected sponsor requires authentication, but skip GitHub enrichment and preserve existing pull-request associations. Recorded pull requests belonging to other chats can still reconcile with their own live sponsors. An explicitly supplied operation sponsor must remain available at capture; background handling does not relax that requirement. Utility completions respect the configured BYOK route; Copilot-routed completions require their own sponsor instead of falling back to another client's or desktop GitHub credential. Legacy Agent Merge attribution remains on the folder's default chat; sponsored operations can use their validated initiating conversation chat without replacing its execution sponsor.

Both algorithms use the same `copilot-sealed.v1` envelope and purpose/resource checks. MC registration/heartbeat keys and AHP root metadata identify the same recipients. Unknown or wrong-purpose key IDs return `CONFLICT` so clients can refresh trusted keys, repeat the handshake, and seal again; malformed, undecryptable, or context-mismatched values return `INVALID_PARAMS`. Private key bytes and owned plaintext buffers are scrubbed on disposal or after use. HPKE opening uses non-extractable WebCrypto private keys; their native storage is managed by the runtime and has no explicit zeroization API.

Native authoritative AHP actions and selected genuine SDK metadata are mirrored to MC for history and task title/activity. Approval/input metadata may contain commands, diffs, plans and questions. The SDK adapter excludes assistant/system messages, auth/configuration, subagents, per-token deltas and routine backing shutdown events; AHP mirroring still carries authoritative conversation content.

Registration accepts unbound sealed tokens for compatibility with deployed pre-sealed clients. Supplied bindings are verified; unbound envelopes remain replayable. Backend tests can require binding through `IMissionControlOptions.requireConnectionBinding`. Optional MCP resource context and MCP completion correlation have the limitations described below and in the matrix. Do not infer stronger guarantees from successful transport authentication.

By default, the SDK's canonical device `remoteControl` branch is read before registration and forwarded to MC for enforcement. Failed initial reads do not register as unrestricted. The host does not introduce a second enterprise-policy parser or claim local enforcement of every predicate against a compromised MC signer.

### Explicit local remote-control policy override

The unregistered, default-off `chat.agentHost.experimentalMissionControl.ignoreRemoteControlPolicy` setting is a testing override available in built products. Set it to `true` in the host owner's **local User settings** to skip the device `remoteControl` policy read and omit that branch from Mission Control registration, allowing active connections despite device enterprise restrictions on creating sessions or sending messages. Application user settings also apply; workspace, workspace-folder, remote-user, and default values cannot enable it. The setting is absent from the Settings UI and schema.

```json
"chat.agentHost.experimentalMissionControl.ignoreRemoteControlPolicy": true
```

This bypasses the entire device `remoteControl` branch, not other runtime managed settings, tool permissions, authentication, or workspace grants. Mission Control can still issue signed passive connections, which remain read-only. Changing the setting closes existing relay lanes and reconfigures registration; reconnect the remote client afterward. Remove the setting or set it to `false` to restore device policy reporting and its failed-read gate.

### User-host credential authority

By default, Mission Control follows the normal Copilot Host User-host authentication model: remote clients supply their own sealed credentials. The host decrypts them, checks purpose/resource and any supplied connection binding, and validates GitHub identity against the registered owner. It forwards the opened client credential and scope metadata internally, using GitHub's reported identity deadline rather than a client-supplied expiry. GitHub `scopes_supported` values are OAuth hints, not local proof of token capabilities; GitHub and the runtime enforce actual access. Native repository operations retain VS Code's separate repository resource, while project cloning uses the requesting connection's GitHub API credential as Copilot Host does. MCP OAuth challenges retain their required-scope checks.

The host owner can explicitly enable `chat.agentHost.experimentalMissionControl.useLocalCredentials` in local user settings. It defaults to false, is application-scoped, and is not synchronized. When enabled, the relay still validates the client's sealed credential and same-owner identity, but its Copilot resource uses the agent host's existing local Copilot credential. The host separately validates the local credential against the same GitHub owner; missing, expired, changed, or mismatched local credentials fail closed without falling back to the client token. Delegation stays connection-scoped and does not update provider-global authentication or replay state. Repository-resource credentials and MCP OAuth tokens remain client-supplied. Project operations using the Copilot resource also use the delegated credential. Changing the setting withdraws existing relay lanes; reconnect clients afterward. Remote clients and workspace settings cannot enable delegation, and enterprise remote-control checks and tool permissions remain in force.

The desktop credential remains available for Mission Control registration and control-plane requests through trusted local management IPC; relay authentication cannot configure it. Rotating that credential, signing out, or withdrawing registration closes affected relay lanes. Reconnect the remote client afterward. Enterprise remote-control checks, workspace grants, and tool permissions still apply.

[`MissionControlHost._attachRelay`](./missionControlHost.ts) enables `scopedRelayCredentials` on Mission Control ingress only. [The relay handler](../protocolServerHandler.ts) lazily creates a source from the host-owned lane owner and credential validator, and forwards that source through authentication, session creation, chat execution, changesets and listener extensions. Wire metadata cannot choose a source or principal. [Scoped authentication](../agentHostAuthenticationScope.ts) does not update the shared desktop credential pool, provider-global authentication, or replay state. Direct local, SSH and tunnel ingress retain their existing authentication paths.

Each connection generation has one current slot per protected resource. Rotation replaces that slot and its scope metadata, including a narrower replacement; new work cannot select an older broader grant. A failed candidate does not erase a valid slot, and competing validation results cannot overwrite a newer accepted credential. A generation's disconnect closes its source and prevents new admission; reconnecting with the same client ID creates a fresh source. An already admitted execution holds a snapshot of its original grant, so ordinary disconnect or rotation does not substitute credentials or automatically revoke that execution's lease. Captures stop being usable at their own known expiry or observed revocation. The host cannot infer remote sign-out/revocation without a delivered signal or invent an expiry for credentials without a reported deadline.

[Session routing](../agentService.ts) persists only the non-secret GitHub API origin and canonical user ID as `vscode.credentialPrincipal`, not tokens or connection IDs. Restored isolated sessions require a usable sponsor instead of falling back to the shared store. Same-principal adoption and token changes take effect at safe execution boundaries; the Copilot backing identity and history are preserved, and active work is not silently recredentialed. Explicit local continuation is a separate local operation: [the authentication service](../agentHostAuthenticationService.ts) validates the chosen local credential directly against the persisted GitHub owner and captures it for that continuation. This is not remote desktop delegation or an automatic fallback when a remote source is missing.

Opening cold history supplies a capture only to that restoration; observing the session does not establish an execution or background-operation sponsor. A subsequently admitted turn establishes its own binding. Warm cancellation, permission responses, drafts and monitoring disablement do not request a new execution credential: an existing turn retains its admitted capture, and scoped callers must still match the session principal. Relay identity authorization remains mandatory, including when an identity expires.

### Scoped Copilot runtime

[The Copilot provider](../copilot/copilotAgent.ts) owns separate lazy SDK clients per scoped chat, pins each launch to its captured grant, and keeps provider-global credential changes/recovery separate from those clients. Prepared turns and SDK launches retain their captured revision. An authenticated client belonging to the same GitHub owner can steer a running turn even when its own credential differs; steering continues under the running turn's credential and does not replace it. Trusted local steering follows the same rule. This matches [Copilot Host's steering implementation](https://github.com/github/copilot-host/blob/db3e5df9d3f3c5581d0a5ce96bdbe864ce1ac518/crates/copilot-ahp-host/src/backend/session_pump.rs#L816). New turns and queued messages use their own caller's credentials at the next safe boundary. A credential change or same-principal adoption relaunches/resumes at an idle boundary without replacing the SDK backing ID. These rules do not provide complete permission isolation between same-owner devices: a steering instruction can use the existing turn's greater permissions.

Scoped launches pass the captured credential as the SDK's explicit `gitHubToken`, including for one-hour token-market credentials. They do not use `gitHubTokenProvider`, whose runtime contract requires more than one hour of remaining lifetime. The host retains the actual expiry and observed-revocation checks for credential capture, SDK launch and execution admission. A client-supplied replacement takes effect at a safe boundary; static SDK authentication does not provide proactive renewal or revoke credentials already handed to running SDK operations. Clients must obtain replacement credentials and authenticate again. Local, SSH/tunnel and standalone AHP credentials keep their existing SDK token/provider selection and one-hour provider refresh margin.

Credential-owned clients use the normal SDK profile with `useLoggedInUser: false`, explicit captured authentication and scrubbed ambient credential/endpoint variables. The caller's token is supplied through `GITHUB_COPILOT_GITHUB_TOKEN` for the agent shell, and through `GH_ENTERPRISE_TOKEN` when targeting GitHub Enterprise. The existing backing-data directory is retained for history continuity. Normal Git configuration and OS-user authority remain available, matching Copilot Host; this is not a sandbox against machine-owned Git credentials. Unauthenticated local metadata/deletion clients use the empty profile without becoming execution sponsors.

[The session launcher](../copilot/copilotSessionLauncher.ts) preserves normal workspace configuration discovery, file hooks, runtime tools/skills, repository instructions and environment context. Existing VS Code settings and managed policy govern Connectors, BYOK/on-device models, session indexing, SDK export and telemetry; credential ownership does not introduce a second feature policy or tool/skill allowlist. MCP OAuth storage remains process-local/in-memory. Startup-setting changes take effect at an idle boundary, with busy subagents deferring configuration-only replacement. Model-boundary tests require matching tool inventories and normalized prompts for local and credential-owned sessions, and verify actual shell, model and Connector credentials.

Agent-derived session/chat creation, message queues, workspace continuations and Agent Merge repairs carry the causing execution's credential source. Those handles stay host-local and are not serialized in AHP actions or conversation metadata. Automations do not yet carry that sponsorship contract: Mission Control does not advertise automation capability, and rejects automation creation/run requests rather than starting later work under a shared credential. Local automation behavior is unchanged.

## Lifecycle and mirroring

The host uses proxy-aware bounded HTTP, a normal heartbeat cadence, and service-requested `Retry-After` waits. Recovery does not bypass those waits; disabling closes ingress even when its offline heartbeat must be delayed. WPS bootstrap/key refresh and relay keep-alive are independent of ordinary inbound traffic.

Host-wide diagnostic log channels are not advertised on Mission Control ingress. Diagnostic logs remain available locally; they do not share the relay's bounded publisher with session operations. This does not change provider-native OTel export.

External sessions are not admitted to either AHP action mirroring or SDK history/live-event replication, even when loaded locally or visible in the local session list. Explicitly adopting an external session clears its external flag and makes it eligible for sharing.

Publishing is independently ordered per client and per `(session, namespace)` mirror stream. A client's responses and notifications share one queue, preserving order across its two destination groups. Different clients and mirror streams can progress concurrently, bounded globally to 64 outstanding publishes and 4 MiB in flight. Fragments of one chunked payload may have up to four publishes in flight, but the next payload in that queue waits for every fragment's acknowledgement. Mirror lifecycle markers wait for earlier frames in both namespaces and block later frames of that session, without blocking other sessions or clients.

Queue limits include in-flight publishes: 512 frames and 64 MiB globally, with at most 128 mirror frames and 16 MiB of mirror traffic awaiting relay acceptance. A bounded reserve of 32 closure notices and 32 KiB allows an overloaded client lane to discard its unsent publications and close without disconnecting other clients. Publication failures on the shared socket still use ordinary relay recovery. Replacement connections have distinct generations; stale predecessor frames/closures are fenced. Request-form compatibility for `dispatchAction` and `unsubscribe` shares the native notification path and does not make arbitrary notifications successful requests.

Clients can advertise receive support with `{ "kind": "capabilities", "accepts": ["batch"] }` on their configured per-client `to-host` group. The host accepts this framing control only from the registered WPS owner on an existing client lane; it is not an AHP request and does not authenticate session access. Support is scoped to that lane and resets on lane replacement or host relay recovery. Clients should advertise after joining their receive groups and re-advertise after each successful initialize/reconnect response. An updated `accepts` list replaces the previous list.

For supporting clients, the ordered publisher packs adjacent already-queued raw AHP messages with the same destination group and host generation into `{ "kind": "batch", "items": [...], "generation": ... }`, with at most 256 items and 900 KiB of serialized envelope bytes. It adds no batching delay. Single messages and oversized payloads retain the message/chunk framing; destination changes and closures remain ordering barriers within a client's queue, while unrelated clients and mirror streams do not interrupt its batches. Each published batch uses one WPS acknowledgement; queue limits still account for the original queued frames and bytes.

History replication uses the existing, separately negotiated `batch-v1` contract. Register and heartbeat responses can advertise `webpubsub.session_events_formats: ["batch-v1"]`; absent, empty, or unknown declarations retain single-frame publication. A heartbeat replaces the declaration without resetting live client lanes, while a token-only refresh preserves the last register/heartbeat declaration. The `sessionEvents` user event can then carry `{ "kind": "batch", "items": [...] }` containing complete replication frames from one environment, session, and namespace, with at most 256 items and 900 KiB of UTF-8 JSON. Original frame identities, sequence order, payloads, namespace credit, and lifecycle barriers are preserved. Batches pack only queued frames, add no timer, and are not chunked. A service acknowledgement releases transport queue credit, not durable spool entries; those remain retained until the ingest watermark covers them.

Clients recognize Mission Control's `host_offline` advisory on the auto-joined environment `.clients` lane. The client validates the group owner/environment and the advisory's environment, offline status, and timestamp, acknowledges relay receipt, and promptly ends the transport so normal authenticated recovery can begin. The advisory is not an AHP message or an authorization grant. Unknown notices are ignored; malformed or foreign advisories do not close a healthy connection.

Independent AHP/SDK spools use durable ingest acknowledgements and bounded failure/truncation signals. Signed backfill replays retained AHP frames exactly. SDK sequence ranges are reserved durably before publication; native journal cursors advance only after durable SDK acknowledgement. AHP process-restart epochs/spool durability and complete pre-registration history remain deferred. Native titles are synchronized through the runtime naming API, not fabricated SDK events.

Mirror streams are per session; a chat belongs to the stream of the session that owns it when each envelope is emitted. When a chat moves to another session, its earlier envelopes stay in its old session's stream, that stream receives `session/chatRemoved`, and the new session's stream receives `session/chatAdded` and the chat's later envelopes. Only a session's default chat is replicated in the SDK namespace, from the native journal of the chat's recorded storage. A chat promoted to a new session's default chat starts that session's SDK stream from the beginning of its journal, since it had no cursor of its own; a default chat that moves under another session, where it is a peer, is no longer replicated, and its old session's SDK stream ends. These two rules await confirmation by the Mission Control owner. Read-only content access reaches the data directories of every listed session and of its loaded chats, including the session a moved chat came from.

## Diagnostics and telemetry

Host registration, relay readiness/recovery, unexpected relay losses and failures are recorded locally in the **Agent Host** log (`agenthost.log`). Client connection milestones and failures use the window log (`renderer.log`). HTTP failures include status and, when available, a request ID and a bounded, credential-redacted server message. WPS rejections and acknowledgement timeouts are also logged. Routine successful heartbeats and individual frames are not logged.

Trace-level publish summaries record serialized bytes, frame count, queue wait, acknowledgement latency, total publication duration, and peak in-flight frames. They do not include payload contents, resource paths, groups, or credentials; publication completion means WPS acceptance, not client receipt or durable ingest.

Relay authorization rejections log the client ID, admission or recheck phase, and whether identity is currently authenticated. Reasons distinguish an unauthenticated identity, invalidated authorization despite a currently authenticated identity, and a closed connection. Standard request-handler failures include the JSON-RPC request ID for correlation with AHP logs. These diagnostics do not include credentials or request contents.

Usage telemetry uses the existing telemetry service and consent:

`agentHost.missionControlPublishSummary` aggregates successful publication bytes/counts, queue wait, service acknowledgement latency, publication duration, queue high-water marks, and bounded failure/backpressure counts while the host is connected to the Mission Control relay service. Background mirroring counts as activity even without an attached phone, browser, or VS Code client; idle periods emit nothing. Publication failures may be reported without a service connection. The host emits at most one summary per five minutes across all clients, mirror streams, and relay reconnects. Errors may trigger an early summary only when that same budget permits; otherwise their counts wait for a later summary. Disconnect and shutdown flushes share the budget; pending healthy-only statistics are discarded when the service connection ends. Shutdown can discard a deferred summary; these events are not a complete error ledger. Timing describes WPS acceptance, not client receipt or durable ingest.

Existing `agentHost.clientConnection` events identify host-observed Mission Control transports through `connectionKind: mission_control` and include the client's optional AHP implementation name/version. Opaque client IDs identify protocol clients, not people or platforms. Clients that omit `clientInfo` cannot be distinguished as mobile, web, or other applications from their protocol version or UUID alone.

- `agentHost.missionControlOperation` reports host configuration, registration, token/key refresh and relay outcomes, plus failed heartbeats/check-ins. Failures include an allowlisted category, known protocol code and validated HTTP status when available, including structured nested causes. `relayDisconnected` reports only unexpected loss of a ready relay, with its ready duration; explicit withdrawal and credential rotation are excluded. Operation failures at different boundaries may describe the same underlying failure and must not be summed as distinct outages.
- `missionControlConnectionAttempt` reports user-local connection success, failure, caller cancellation and timeout across inventory validation and relay establishment, with bounded failure metadata. An environment observed offline has the explicit `offline` category. This distinguishes the retained-host service's end-to-end deadline from the cancellation it sends to the shared relay service.
- `userLocalRelayConnectionOutcome`, `userLocalRelayFirstSessionRequest` and `userLocalRelayConnectionHealth` report `environmentKind=user-local`. Outcomes cover logical connects and recovery, including failure and cancellation. Health aggregates ready connection time and unexpected disconnects, excluding initial retries and intentional teardown. The shared tracker retains the `cloudSandbox*` event names and payloads for cloud environments; each sample emits only one event name. Historical user-local samples use the `cloudSandbox*` names with `environmentKind=user-local`, so cross-version analysis must include those filtered historical samples.
- `agentHost.clientConnection`, `agentHost.sessionCreated` and existing action/turn events identify user-local relay traffic with the bounded connection kind `mission_control`, alongside `ssh` and `dev_tunnel`. The host knows its relay route even when another conforming client omits VS Code metadata. Session creation is counted after successful AHP allocation, not discovery or restoration.

No error messages, stacks, response bodies, credentials, environment names, request IDs or addresses are added to these telemetry events. Failure categories come from exact known error names, allowlisted protocol/network codes and validated HTTP statuses, never message parsing. Unknown codes are omitted rather than hashed or forwarded. Server error messages remain local. Host-wide logs are not exposed over Mission Control ingress.

`userLocalRelayFirstSessionRequest` samples the first session create, list, or subscribe RPC after readiness, excluding the root subscription used during handshake authentication. Its `requestKind` distinguishes listing, creation, root, session, chat and other subscriptions. Failures carry only bounded category/code/status metadata. Connection outcomes retain the first failed phase's `firstFailureCategory` and `firstFailureStatusCode`, even if retries later succeed.

`userLocalRelaySessionOpen` samples the first managed **session** subscription started while ready in each user-local connection cycle. It ends when a snapshot is received, the request fails, or the connection is lost or disposed. It excludes root/chat subscriptions, listing, repeated subscriptions in that cycle, and the automatic restoration performed before readiness. `connectionOperation` distinguishes initial connection from recovery; `attemptId` is the client-generated protocol attempt UUID shared with the first-request observation. It measures snapshot receipt, not application/rendering or proof that the user read the session. Existing restoration-phase telemetry covers automatic reconnect restoration. A missing sample can mean no qualifying open, an unfinished request, process termination, or telemetry loss; it is not a successful zero-duration open.

Existing `agentHost.sessionSubscribe` events add the subscribing client's bounded type, connection kind, launch kind, opaque client ID, and a hash of the owning session resource. Session and chat channels for the same session share that hash; no session URI/path is emitted. Count distinct `(host, clientId, sessionIdHash)` tuples to deduplicate subscription activity, filtering `connectionKind=mission_control`. `isReconnect` describes the transport's handshake, not whether a later subscription is restoration. These host timings end before network delivery and are not user-view or paint counts. Client timing samples cover instrumented VS Code clients; other clients still contribute host subscription events but must implement their own client-side timing.

At most one new `userLocalRelaySessionOpen` outcome is emitted per ready user-local connection cycle. All other additions enrich existing events without adding starts, per-frame records, timers, polling, or RPCs. Existing usage-telemetry consent applies. Failures, disconnects and late completions settle pending client observations once; a hard process termination can leave no outcome. `agentHost.invocationFailed` continues to cover chat invocation failures, not opening existing sessions.

## Implementation ownership

Source files live alongside these documents. [MissionControlHost](./missionControlHost.ts) is an entry-owned DI adapter for native services, handler lifetime and authoritative mirror wiring. [MissionControlEnvironment](./missionControlEnvironment.ts) owns registration/recovery through a named host-options contract; it has no second runtime service graph.

Registration and heartbeat request construction are separate methods. Local management IPC is distinct from AHP; host-management extension methods remain unavailable to relay clients. The same `ProtocolServerHandler` owns session operations on both local and relay transports.
