# Production gaps for a user-local Mission Control environment

This is the production-readiness checklist for the [development prototype](./MISSION_CONTROL_PROTOTYPE.md). It covers security, lifecycle, protocol compatibility, distribution, and validation. "Current" describes this TypeScript implementation, not capabilities implemented by a different host or a guarantee about every deployed Mission Control client.

> [!WARNING]
> Live mode exposes native sessions to the authenticated environment owner. MC filesystem requests are rooted in locally known workspaces, with per-session content readable but not writable through that grant. This is not per-session credential sponsorship, OS confinement, or end-to-end encryption of the conversation. The security checks already implemented below do not establish those missing properties.

## Scope of this hardening pass

Mission Control-specific defects are repaired without redesigning pre-existing normal Agent Host security behavior. Restrictions beyond the current Copilot app's enforced behavior are recorded for later review, not silently imposed on this integration. This parity target is not a security certification of either implementation. Mandatory connection binding and the full native session-URI/persisted-state migration are explicitly deferred. Global credential sponsorship, OS containment, and shared normal-server resource/logging behavior require separate review before claiming their stronger protections.

### App-parity completion boundary

The development implementation now includes registration, owner-bound withdrawal/credential refresh, live workspace grants, profile-copy identity separation, relay recovery/keep-alive, native discovery and passive interactivity, sealed MCP authentication, and bounded AHP mirroring/backfill. These paths have focused regression coverage. A real two-window exercise additionally verifies the new picker without a test adapter, local and remote turns on one native conversation, manual reconnect, owning-host restart followed by another remote turn, and MC task association and durable AHP history containing the two pre-restart test turns.

The remaining release gates are not silently reclassified as implemented:

- Existing sandbox regression validation is blocked by the tested environment's absence: its record reports offline and its connect endpoint returns `404 environment not found`. Recovery stops on a permanent broker refusal instead of dialing an unservable lane; no replacement compute is provisioned.
- Windows/Linux and signed release-package/crypto loading, enterprise/proxy/certificate environments, sustained outages and load-shedding deployment behavior still need validation in those environments.
- Mirroring only the admitted authoritative stream does not reconstruct pre-registration history or supply restart epochs. The applicable portable contract supplies no complete initial-history snapshot/epoch flow; process-restart durability beyond the agreed parity target remains deferred. The live check proves stored pre-restart turns, not continuity of the same mirror stream across restarts.
- Stronger policy/limits, managed-compute principals, mandatory credential binding, OS isolation, shared-provider sponsorship, full URI migration, and the separately noted response-part ID continuity must not be introduced or claimed as completed under this app-parity pass.

The canonical runtime's device `remoteControl` document is reported opaquely to MC, its enforcement point; the initial read must succeed. The SDK supplies a read operation rather than an authoritative change notification, so the real host polls at check-in. A client-permission-change event is not substituted for a device-policy event, and no duplicate enterprise parser is added.

## Trust boundaries

- **Control plane:** the trusted local workbench supplies the registration credential over management IPC. Mission Control is a peer, not an authority to replace local policy, credentials, configuration, or executable code.
- **Transport:** a Web PubSub JWT authorizes specific transport lanes. It does not establish the GitHub principal or credential that sponsors agent work.
- **Agent identity:** a separately presented GitHub credential must resolve to the registered canonical owner. Same owner does not mean same permissions: two devices can hold differently scoped tokens.
- **Key discovery:** authenticated HTTPS or trusted local bootstrap establishes the host's sealing key. A key received only over the relay cannot authenticate the endpoint presenting it.
- **Agent execution:** tool approval, filesystem authorization, OS confinement, and credential isolation are separate controls. Passing one must not bypass another.

## Security checklist

### 1. Seal credentials before publishing them

- **Current:** [missionControlAuthentication.ts](./node/missionControlAuthentication.ts) opens sealed GitHub and MCP credentials with separate purpose keys and verifies the inner purpose/resource context when a resource is supplied. Raw relay `authenticate` tokens are rejected. Direct/local authentication is a separate compatibility surface. The [client transport](./browser/webPubSubRelayTransport.ts) refuses plaintext authentication before publication and redacts authentication tokens, including sealed ciphertext, from its transcripts; the existing sandbox client requires a pre-sealed token. User-local MCP authentication pins the HTTPS environment key against the live host advertisement, then seals through stateless trusted-local management IPC with the exact resource and any advertised handshake challenge. The raw credential never crosses WPS; the sealing operation is not exposed through AHP. This covers `authenticate`, not arbitrary secrets embedded in other configuration or message content.
- **Before shipping:** make refusal to publish plaintext mandatory in every relay client path, including token refresh and MCP authentication. Host rejection after receipt cannot undo disclosure to Azure. Define supported algorithms and key rotation/overlap; implement HPKE if required by the supported client matrix rather than assuming sealed-box support everywhere. Keep private keys host-local.

### 2. Authenticate the host's advertised key

- **Current:** [missionControlEnvironment.ts](./node/missionControlEnvironment.ts) publishes public keys through registration/heartbeat as well as AHP root state. Independent-client tests used the authenticated MC HTTPS copy. No dedicated trusted local endpoint-record advertisement of these sealing keys is implemented by this prototype.
- **Before shipping:** require clients to obtain and authenticate an out-of-band key bound to the intended owner/environment, compare it with the handshake advertisement, and handle restarts/key changes without silently trusting a relay replacement. For direct connections, use an authenticated launcher/IPC or endpoint-record equivalent; a same-user file is not protection against an unconfined process running as that user. Never place credentials in a discovery record.

### 3. Require connection-bound, replay-resistant credentials

- **Current:** a handshake challenge, nonce/timestamp validation, and bounded replay ledger exist. `requireConnectionBinding` is optional and defaults to false; an unbound sealed credential can still be replayed. MC token resealing is implemented and pre-sealed authentication worked in live tests, but that is not evidence of connection binding or adoption by every deployed client. Connect/reconnect can omit a sealed token when no usable key is available.
- **Deferred compatibility boundary:** keep existing unbound MC tokens usable in the development experiment until supported clients/services adopt binding. The identity gate therefore proves possession of a sealed owner token, not that its presenter is the original client; observed unbound credentials can be replayed. Optional MCP resource context preserves the existing contract too, so a credential without that context can be retargeted to another MCP resource. These are accepted compatibility risks awaiting review, not production-secure protections against a compromised relay or control plane.
- **Before shipping:** complete the native/web client and service flow needed to bind credentials to the current handshake generation, then require binding across the supported fleet. Test stale challenges, nonce reuse, clock skew, reconnect, and rotation. Missing keys or sealed tokens must fail closed with an actionable error, never a plaintext fallback. Validate token audience, resource, repository scope, and compatibility of any MC-minted credential.

### 4. Separate connection access, session authorization, and the driving credential

- **Current:** signed spawn, publisher-owner checks, and lane/client-ID binding constrain relay ingress; presented GitHub identity tokens are validated against the canonical owner. Each live lane needs its own identity authentication before requests/dispatches; a new handshake clears authorization and stale identity responses cannot authorize the new generation. Collision rejection covers client IDs another protocol handler currently remembers; reuse after history expiry or restart still needs review. Passive identity validation does not install provider credentials. The pre-authentication root snapshot contains no config values, terminals, or customizations; session snapshots and MCP notifications are withheld until identity validation, and the native WPS client refreshes root state after authentication. Host-wide configuration is excluded from relay root snapshots and updates even after authentication because MCP environment/headers and proxy values can contain credentials.
- **Existing shared architecture, deferred:** [agentHostAuthenticationService.ts](./node/agentHostAuthenticationService.ts) stores credentials by protected resource/scopes and replays them to providers, not by client/generation. A non-passive relay authentication still replaces shared provider credentials, can finish installing them after the lane closes or MC is disabled, and does not revoke those credentials on lane disposal. The lane's identity gate is not proof of provider acceptance or of which token sponsors agent work. This behavior requires a separate native credential-sponsorship repair; suppressing a disconnected reply is not a fix.
- **Filesystem boundary:** [protocolServerHandler.ts](./node/protocolServerHandler.ts) gates MC `resource*` calls, terminal cwd, session creation, and working-directory additions against locally known roots. Known-session database/git diff references are readable, including references bound to non-default chats. Pending-edit permission previews additionally require the exact URI published by authoritative pending-confirmation tool state in one of the owning session's chats, including worker chats whose previews retain the parent's storage URI; they stop being authorized when that state retires. Unknown-session references, non-file writes, and side-effectful attribution URI reads are not allowed. Per-session content roots are read-only, dangling symlink destinations are denied, and terminal cwd must be an existing granted directory rather than falling back to home. The ordinary local/direct server's grants remain unchanged. This is path authorization, not an atomic filesystem sandbox: symlink replacement after validation, hard links, agent shell execution, existing terminals, and alternate routes such as persistent automation need separate review.
- **Shared preview storage, deferred:** the existing in-memory pending-edit filesystem keys by path, ignoring URI authority. MC authorization therefore checks the exact published reference rather than trusting an authority-only session binding. Shared storage still needs an independent review of collision/isolation behavior when distinct sessions reuse the same tool-call ID and file path.
- **Pre-existing git content reader, flagged:** the ordinary [git service](./node/agentHostGitService.ts) passes a caller-provided blob ref into `git show` without an option terminator. The MC read gate rejects empty and option-shaped refs while retaining ordinary refs such as `HEAD`; the class-level normal-server git argument hardening remains a separate review item.
- **Before shipping:** authorize create, observe, steer, filesystem access, reverse requests, and client-contributed resources against the acting connection and session. Verify minted WPS JWT roles only allow the intended owner/environment/client lanes, and scope data-plane/mirror publication to its owning environment/session. Bind credential records to client plus generation, capture the creating credential, and re-pin agent/host-side API work to an authorized driver on handoff. Never union scopes, retain a broader previous credential, or use registration/ambient/local-provider authentication as implicit authority for a remote client. Define sponsorship lifetime on disconnect and reject stale in-flight authentication results. Preserve passive/read-only enforcement and keep VS Code host-management extension methods unavailable over WPS.

### 5. Protect credentials throughout their lifetime

- **Current:** private sealing keys and opened plaintext byte arrays are scrubbed; WPS authentication fields are redacted before transcript logging. This does not zeroize immutable JavaScript token strings or provider-retained copies, nor repair the ordinary shared server/logger. The native auth service uses the client's `expiresIn` hint; this is not an authoritative GitHub expiry check. There is no demonstrated end-to-end guarantee covering arbitrary secret-bearing configuration, SDK output, crash reports, or all credential disposal paths.
- **Before shipping:** redact raw and sealed credentials before any wire/runtime logging, telemetry, debug-log export, persistence, or mirroring; audit [ahpJsonlLogger.ts](./common/ahpJsonlLogger.ts) and its callers rather than assuming protocol logs are safe. Minimize secret copies/retention, clear references and scrub owned buffers on replacement, revocation, sign-out, session end, and shutdown. Use authoritative expiry/revocation and bounded credential age, not a client assertion. Refresh the MC credential only from the trusted local authentication lifecycle and validate each replacement against the pinned identity; do not add an MC-pushed credential or daemon-style token-file requirement to the workbench.

### 6. Authenticate every control-plane command

- **Current:** [missionControlControl.ts](./node/missionControlControl.ts) verifies ES256 spawn and backfill signatures, freshness, nonce replay, environment/owner binding, and signed/outer field equality. A spawn opens a transport lane, not an agent session; backfill only replays that environment's retained AHP frames. HTTPS signing-key refresh validates keys and retains the existing replay ledger across rotation and socket recovery.
- **Before shipping:** establish an independently trusted MC signing-key source, rotation/revocation policy, and bounded replay handling across reconnects. Treat control-group membership as insufficient. Keep acted-on fields bound to the verified payload. Any future backfill handler needs the same verification, session-owner authorization, and resource limits; unsupported/unsigned commands must never acquire a fallback action path.

### 7. Enforce local consent, policy, and limits even if MC is compromised

- **Current:** the device's canonical `remoteControl` policy is read before live registration; an initial read failure does not silently register as unrestricted. Passive lanes and a fixed 32-lane implementation cap exist. They are not a complete local authorization policy, configurable active-session cap, or lane-opening rate limit.
- **Before shipping:** make operator/user-owned policy authoritative, compose enterprise/account/device restrictions fail closed, and revoke already connected clients when policy or consent changes. Define explicit project/resource grants, allowed session providers and repositories, any runtime slash-command restrictions, active-agent-session limits, and a rate limit on new relay-lane openings with intentional safe defaults. A slash-command policy is not an OS shell sandbox. MC must not override these controls, install binaries, mutate local configuration, or broaden grants through signed commands.

### 8. Define user-local versus managed-compute security boundaries

- **Current:** registration accepts a canonical user-local owner, not organization/application runtime principals. Live control-plane HTTP requires an HTTPS origin and rejects redirects; the fake endpoint is loopback-only. GitHub identity validation uses the native GitHub endpoint service's HTTPS API base independently of the MC origin, retaining Enterprise API paths and pinning the authority for the environment lifetime. Changing that authority withdraws MC access and requires an Agent Host restart before configuring the new authority.
- **Before shipping:** separate trusted GitHub/enterprise identity authorities from custom MC origins and bound bearer destinations; validate WPS bootstrap destinations and proxy/certificate behavior. Keep organization/application principal and provisioning/attestation capabilities absent from the general user-local build, not merely disabled by a setting; a managed variant requires a separately reviewed deployment/build boundary. Any managed variant needs independent principal attestation, per-environment/VM-scoped credentials, and cloud-specific isolation: block IMDS, constrain egress, and define mandatory privacy-reviewed session/audit mirroring where it is a compensating control.

## Agent containment and content privacy

- **OS enforcement is still open:** define workspace/network isolation and explicit, auditable capabilities for access outside the workspace, credential stores, internal networks, or privileged sockets. Do not launch elevated/root agents; isolate the host's config, credentials, and registration state from agent code. Require reliable process-tree cleanup, including on disconnect/session shutdown and crashes. Tools cannot grant themselves capabilities. Approval tiers alone are not confinement.
- **Encryption scope is limited:** sealing protects selected credential fields from the relay, not prompts, tool results, files, or the full AHP stream. MC pre-sealing also does not hide the input credential from MC itself. Define exactly what the relay and MC can observe, what mirroring uploads, its retention/access controls and consent, and whether any additional content encryption is required.
- **Distribution needs validation, not a blanket claim of being unsigned:** preserve VS Code's existing signing/notarization and update-verification guarantees, and verify the new crypto dependency in release bundles on every platform (license, embedded WASM/loading, ASAR, and runtime availability). No independent MC-triggered updater is required or permitted. Keep network destinations documented for operators.

### Deferred response-part identity compatibility

Recorded on 2026-10-02; do not implement until this item is resumed. Native Copilot history reconstruction in [mapSessionEvents.ts](./node/copilot/mapSessionEvents.ts) assigns fresh UUIDs to markdown and reasoning response parts. Reconstructing identical persisted input twice reproduces identical content with different part IDs. A consumer that retains displayed history and checks its message/reasoning identities against a recovery snapshot can consequently reject that snapshot as omitting displayed messages, even when its turn count is complete. Live part IDs originate independently in [copilotAgentSession.ts](./node/copilot/copilotAgentSession.ts), so making reconstruction deterministic alone would not preserve live-to-restored identity. This is a consumer compatibility requirement, not a newly established AHP requirement that every part ID survive every cold restart. Future work must decide and test identity continuity across live delivery, reconnect, history reconstruction, and host restart without weakening content-preservation checks.

The native WPS client refreshes public root state after authentication, using a single-flight, bounded snapshot refresh that buffers intervening root actions. This also affects existing cloud-sandbox connections: re-subscribe is standard AHP, but a live sandbox smoke test remains a release validation requirement. These relay clients no longer forward local host configuration or managed-permission overrides to their remote host.

Before replacing a brokered WPS transport, the client mints a fresh ticket for the same client ID so recovery can reopen a reclaimed lane and obtain current sealing material. Broker responses may reuse unchanged ciphertext/key metadata; periodic and reconnect paths share the same merge-and-validation helper. A late periodic refresh cannot overwrite a newer recovery credential. Permanent broker refusals stop recovery; transient faults retain bounded backoff and waking delays. Real host-restart recovery completes in the exercise and a subsequent remote turn succeeds; this is distinct from the deferred response-part identity and durable mirror restart guarantees.

### Platform contract alignment

The cross-platform environment and client design adds these acceptance criteria beyond a working relay:

- Preserve the selected target's execution owner: a local endpoint must not impersonate SSH, WSL, or container targets, and an unavailable environment must not silently start replacement compute.
- Pair stable environment identity with an owner incarnation; reconcile generation and session/chat baselines before restoring control. A live WPS connection is not proof of host or callback/tool availability.
- Reconcile interrupted create/send outcomes under the original owner. Request IDs are not durable idempotency; reserve and record create intent/outcome, handle lost replies without duplicating work, and clean only resources owned by the attempt.
- Late subscribers must see already-pending approvals, questions, and client-tool requests; completion settles the original continuation once. Attaching is not importing, cold-resuming, or duplicating execution.
- Keep turn cancellation, archive, dispose, deletion, client disconnect, and owning-host shutdown distinct. Opt-out withdraws remote access without deleting local work, history, or checkouts.
- Keep version/capability offers, paginated catalogs/history, HTTP connection-ticket recovery, and AHP replay/snapshot recovery separately testable. Do not equate a package pin with the wire versions all clients actually offer.
- Token exchanges must preserve the originating principal and cannot widen its authority. Scope, issuer/audience, lifetime, and driver sponsorship are not implied by successful transport authentication.

These are product/host acceptance criteria, not proof that every client or MC deployment implements them. Managed-compute principal support and fleet-wide connection binding remain externally coordinated boundaries. Pre-existing normal Agent Host security behavior is recorded for separate review; this work repairs newly exposed MC paths without claiming a general-server security redesign is complete.

## Evidence required before production enablement

The current tests and live exercises establish a functional relay, not completion of this checklist. A release decision needs:

- Cross-client conformance for sealing algorithms, authenticated key discovery, missing-key refusal, mandatory binding, MCP credentials, and no plaintext publication or secret-bearing logs.
- Deterministic multi-client tests for differently scoped same-owner tokens, driver handoff, passive mutation rejection, unauthorized observation/resources, generation changes, revocation/expiry, and isolation from the local/control-plane credential.
- Forged/unsigned/stale/replayed control tests, malicious signed-but-policy-disallowed requests, bounded lane/session/resource pressure, and key rotation.
- Host/client restart, lost sockets with live relay connectivity, repeated spawns, expired WPS tokens, service failures/`Retry-After`, and reconciliation tests that prove recovery without duplicate state application.
- Cross-platform OS containment/process cleanup and signed release-package/crypto-loading checks, plus enterprise/custom-origin/proxy/certificate coverage.
- Explicit decisions and responsible components for every remaining boundary above. User-local enablement must not implicitly enable managed-compute principals or claim protections supplied only by a different host.
