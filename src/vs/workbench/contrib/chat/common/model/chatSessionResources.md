# Local chat binary persistence

## Contract

Local session metadata stores versioned binary descriptors, never repeated copies of recognized attachment or tool binary payloads. A descriptor contains a SHA-256 digest, byte length, and the original representation. Blobs are immutable, addressed by digest, and deduplicated **within a session**. Files and remote URLs supplied as references are not copied; only already-provided inline bytes are persisted. Original attachment references and omission/authorization metadata are preserved.

The session's sibling `.resources` directory owns its blobs. A save writes and verifies new blobs before committing metadata. Binary sessions write a complete reference snapshot using the file provider's atomic-write capability when advertised; providers such as IndexedDB use their native write semantics. Unchanged operation-log saves do not rewrite the snapshot or blobs; flat-format saves replace only the reference-sized metadata. Text-only sessions retain incremental logging. Failed blob writes leave the previous metadata intact; failed metadata writes do not advance the operation-log checkpoint. Retry can repair incomplete or corrupt blobs when valid inline bytes are still available. Garbage collection only removes superseded blobs after a replacement snapshot commits, not while committed metadata still references them. Orphan directories and incomplete writes are recoverable after a crash.

Loaded descriptors become lazy references. Opening a session reads metadata, not blobs. A read verifies the exact byte length and digest and reports unavailable/corrupt content as an error. Rendering, image extraction, copying, exporting, and participant invocation resolve only at their consumption boundaries; they never substitute empty bytes. A formerly committed resource that is later lost or corrupted becomes an explicit unavailable descriptor on the next save, so unrelated new text remains durable. Historical requests present an explicit unavailable-resource notice instead of inventing image bytes; newly attached missing data and portable export still fail. Portable JSON export stages the stream before replacing its destination. Cancellation does not discard durable resources.

An in-memory fork retains its source resources until it is disposed. Before persisting a fork or workspace transfer, referenced bytes are copied into the destination session's own resource directory. Deleting the source cannot invalidate the persisted destination. Requests, responses and drafts update their ownership when their contents change. Disposed input and attachment models never acquire new leases from late composer flushes or folder-resolution callbacks. Cross-window shared blob leases protect live readers and forks. Migration reads stored reference manifests, merges only their immutable blob files, validates existing destinations before reuse, and stages and verifies copied bytes before publishing metadata. A partial or corrupt destination is repaired on retry without replacing a directory that may still contain leased data. Verified staging files can be recovered even if the source subsequently disappears. Ordinary saves use the same destination/staging-first recovery, so a mounted draft retaining an old source reference cannot discard bytes already recovered at its destination. If no valid copy remains for a missing or corrupt source blob, migration preserves the transcript, draft or history and its healthy images, marking every affected reference explicitly unavailable. Real I/O failures still block publication. Owned-input migrations retry automatically; failed transcript copies preserve their original files and report the failure, without an automatic retry. Automatic trimming retains the existing index-only policy: transcripts and their owned blobs remain available to lazily restored editor tabs and hidden views. This change bounds binary duplication, not total user-owned history with a new disk quota. Explicit deletion removes metadata, even for an index-trimmed session, but defers deletion of leased blobs.

All storage transactions share a cross-window mutation lock. Before starting a transaction, native storage drains admitted mutations and issues fencing tokens so delayed writes from a terminated renderer cannot commit after another renderer's collection. IndexedDB storage refreshes its metadata cache from the database. Blob preparation, metadata publication and cleanup run under the same lock, and cleanup derives reachability from committed metadata rather than a window-local cache. A durable, validated cleanup ticket is written before mutations that could orphan blobs. Deferred, per-ticket recovery retries after outstanding owners release their leases and on later startups; startup does not parse every session. No cross-session reference counts are persisted. Owned input remains workspace-ID-specific even in empty windows, whose transcript catalog is intentionally shared. Workspace transitions copy each input owner independently of transcript migration; failed copies retain their source and retry on subsequent reads, storage flushes and shutdown in that window. Live input caches invalidate their saved-state assumptions after a failed migration, so an unchanged draft can be republished. Cold handoffs await saved-draft hydration before deciding whether an incoming draft may replace it.

Legacy flat JSON and operation logs remain readable. Their inline values migrate on the next successful save; old data is not deleted before the replacement metadata is durable. Portable exports resolve descriptors back to the existing inline format; imports cannot use internal storage descriptors or resource capabilities to obtain local files. Public extension attachment types remain unchanged. Internal references do not authorize a new source-file read or bypass content exclusions.

Only Markdown media destinations are rewritten: code samples, prompts, tool inputs and literal capability-looking text retain their original meaning. Redundant data-URL translation-map entries are omitted; semantic tool resource URIs, audiences and source authorization references survive restoration and export. Portable draft handoffs and clipboard data materialize their bytes before serialization instead of persisting detached internal descriptors. Internal input history and draft caches have independent owners under the workspace's private input storage: they persist references and retain live/pending snapshots, and eviction commits the smaller metadata snapshot before collecting bytes. Imported drafts retain text and inline images, but cannot select permissions, models or executable context from the import.

Failed input-history or draft loads are logged and leave the in-memory or legacy value usable. Loading retries with capped backoff; unread drafts remain unready for automatic handoff, and a failed read alone never overwrites unknown saved input with an empty fallback. Successful retries restore bound composers without overriding newer edits. History appends and moves remain pending across repeated I/O or unknown failures, and are replayed only after a successful read; saves report the unresolved failure rather than publishing partial history. Only confirmed JSON/shape corruption or an explicit history reset permits replacing unread history. Unsupported versions are not treated as corruption. Explicit edits can replace a single draft. Saves admitted before composer disposal complete without accepting new updates from disposed owners. Retry timers stop on disposal and after the joined shutdown save. Owned-data envelopes validate their owner-specific shape while retaining legacy history entries.

Pending messages retain provisional ownership while their images are resolved. Unrelated streamed updates cannot remove a new message or overwrite an in-flight image edit; actual remote edits and consumption remain authoritative. Other text messages, removals and reordering are published without waiting for image reads. Failed image reads report an error and retain the local request for editing, retry or cancellation.

Atomicity is the file provider's guarantee; this does not add atomic writes to providers lacking them or a stronger physical-media/fsync guarantee than the existing file service. Outgoing model requests necessarily materialize their requested bytes. Portable exports stream JSON instead of constructing a session-sized string. New live responses can retain their provider-supplied payloads until model disposal; this change bounds their persisted representation and reload, not provider or network memory. Independent MCP sampling-log retention is outside the local session store. Older VS Code versions do not understand the new internal binary descriptors; portable exports remain inline. Browsers without Web Locks can still read sessions and save text-only sessions, but explicitly reject binary writes and storage migration; resource collection is disabled there rather than using unsafe instance-local locking.

## Reproduction

Build client output with `pnpm run build-fast -- --client-only`, then run `node --expose-gc scripts/chat-simulation/benchmark-session-storage.mts`. It uses the actual chat model, operation log, session store, file service, and disk provider in a temporary directory beneath this checkout's `.build`; it removes its session data after each run.

Run `node --expose-gc scripts/chat-simulation/benchmark-session-storage.mts --baseline d041bd1a3183ba62a0fafb880d2bce0ec3aa3b99 > .build/storage-baseline.json` for the original implementation. This compiles the changed, pre-existing source modules from that revision under `.build` and substitutes them through a process-local Node module hook; it neither changes the current build nor checks out another branch. Both variants use the same installed dependencies. Run variants sequentially, not alongside builds or tests. `node --expose-gc scripts/chat-simulation/benchmark-session-storage.mts --compare .build/storage-baseline.json` also asserts metadata below one percent of that measured baseline and text-heavy unchanged-save medians no greater than twice that baseline, allowing run-to-run noise without accepting the multi-second regression that motivated this check.

The scenario has eight distinct 2 MiB synthetic binary payloads (16 MiB total). Each occurs in a sent attachment, tool output, result metadata, and the draft. Five runs measure initial save, ten unchanged saves before and after hydration, disk bytes, blob counts, metadata bytes, reload including model hydration, and post-GC retained heap/array-buffer deltas. Separate 300-turn Markdown sessions measure unchanged saves with 20 KiB and 200 KiB per turn, including ordinary `data:` type annotations and object properties that must not trigger binary Markdown parsing. The synthetic bytes test storage, not image decoding. Rendering is covered separately with valid image fixtures.

The unmodified baseline at `d041bd1a3183ba62a0fafb880d2bce0ec3aa3b99` writes 89,487,653 bytes (about 85.34 MiB) for those 16 MiB of unique bytes. Unchanged saves already append zero bytes, but re-encode/clone the payloads. The concrete structural targets for this scenario are one blob per distinct payload, no binary reads during hydration, zero growth on unchanged saves, and metadata below one percent of baseline. Timing and heap measurements are reported as observed comparisons rather than universal guarantees.

These are disk-persistence microbenchmarks, not whole-workbench startup or provider benchmarks. Heap deltas describe retained allocations after GC, not peak memory. Native binary sessions replace their reference-only metadata atomically on changed saves; text-heavy sessions containing binary data may therefore write more metadata than an incremental text-only log. Portable import still parses the existing inline JSON format in memory; this change does not add a streaming JSON importer.

The same harness also measures adding a request to 300 text-only turns of 200 KiB each, then streaming 500 Markdown chunks after 60 tool results of 80 KiB each. Five-run medians were 0.075 ms / 0.168 ms for adding a request and 0.0015 ms / 0.0024 ms per streamed chunk (baseline / resource storage). These very small absolute measurements are informational, not statistically established performance guarantees. Reference ownership changes process newly inserted content rather than rewalking all prior tool results on each chunk. Text-only saves use the existing serializer without binary externalization, and Markdown without data/resource targets bypasses the lexer.

Focused tests cover legacy flat/log and numeric-object image migration, write and transfer-index failure/retry, deduplication, cross-window deletion and fork ownership, dynamic draft/request ownership, prepared-blob collection races, index-only trimming, deferred recovery, owned input-history eviction, late empty-draft hydration, synchronous input acceptance, queued inputs, JSON and ZIP export, cancellation, source references, safe draft imports, participant-readable bytes, actual MCP webview structured cloning, clipboard handoff, and real DOM rendering after reload (including missing/corrupt images). Native-channel tests cover admitted writes/deletes/copies, stale fencing tokens and open handles; an Electron test connects the production workbench adapter to its native channel, and browser tests use actual Web Locks and two IndexedDB connections. ZIP export uses an owned temporary JSON file and the existing native streamed-entry API rather than a giant IPC string.

An isolated authenticated Code OSS run explicitly selected the Copilot SDK harness and completed a sign-in verification response. A synthetic 64×64 PNG survived draft reload, request submission, transcript reload and input-history restoration; the model identified its blue background and white center. Typing a new draft immediately after sending did not erase it. The actual history stored one integrity-verified 329-byte blob with 4,778 bytes of metadata and no inline base64. Actual JSON and native ZIP exports retained the exact draft-image bytes. Live testing also reproduced and corrected a late empty-composer hydration race; a new unsent image draft then survived reload. This was Copilot SDK workbench validation, not a Local-harness run.

A separate Agents-window run, before the final failure-recovery revisions, also explicitly selected Copilot, verified sign-in, and used the existing assigned branch rather than creating a worktree. Its unsent image draft survived reload with 914 bytes of owned metadata and one verified 329-byte blob. A subsequent unchanged save/reload preserved both metadata size and modification time. Physical crash/power-loss and Windows/Linux execution remain untested.

After the recovery and pending-message revisions, a fresh authenticated Copilot workbench run repeated draft reload, image recognition, and history restoration. An image restored from history was submitted as steering during an active 500-line response and reached the model without losing its message; the completed image and reply survived another reload. Four history entries containing three image occurrences used 9,663 bytes of metadata and one integrity-verified 329-byte blob. An unchanged reload preserved metadata size and modification time. A live-discovered disposed-input lease leak was reproduced by a failing lifecycle test, fixed, and checked in another fresh authenticated copy: five Copilot selections and three forced garbage collections produced no disposable warnings.
